# נדרים פלוס — תשלום בשיטה 3

## מסלול הקנייה

בדף הספר ובסרגל הנייד יש כפתור ״קנייה עכשיו״ שמוסיף את המהדורה שנבחרה ומעביר ישירות לקופה. ההוספה לסל נשארת זמינה לקניית כמה ספרים, ובחלונית הסל אפשר להגיע ישירות לתשלום או לבחור בעריכת הסל.

כאשר נדרים הוא הספק היחיד והמשלוח במחיר קבוע, הקופה מציגה פרטי לקוח, כתובת, משלוח ואישור תנאים בדף אחד. לחיצה אחת על ״לתשלום״ שומרת את הפרטים והבחירה במשלוח, פותחת או משתמשת בסשן מתאים, שומרת אישור תנאים בשרת ומכינה את העסקה. בחירת האמצעי עצמה נמצאת בתוך האייפרם. הטופס אינו מסמן מראש הסכמה לתנאים או לדיוור, ואישור תשלום בדפדפן עדיין אינו מאפשר השלמת הזמנה ללא אישור שרת.

מחוץ לאייפרם אין כותרת ספק, רשימת ארנקים או הסבר טכני על הסליקה. הודעות מצב ושגיאה נשארות כשנדרשת פעולה. למשלוחים שמחירם מחושב לפי הכתובת, לתשלומים אחרים ולכרטיסי מתנה נשמר המסלול הקיים, כדי שלא לבחור משלוח לפני שניתן לחשב את מחירו. שתי אפשרויות המשלוח המקומיות הנוכחיות הן במחיר קבוע.

בהכנת התשלום ובאימותו מופיע מסך עיבוד עם עיגול בצבעי החיפוש של האתר. חלון modal מקורי של הדפדפן חוסם לחיצות ומקלדת בשאר העמוד. הצלחה מוצגת רק לאחר אישור שרת; סירוב מהאייפרם נבדק מול השרת לפני הצגת כישלון. אם האישור מתעכב יותר מדקה, מוצגת המתנה עם אפשרות לבדיקה חוזרת, והאייפרם נשאר חסום לתשלום נוסף. המתנת bit/העברה לאישור באפליקציה משאירה את ה־QR והקישור נגישים בתוך האייפרם.

ההטמעה משתמשת באייפרם v3 עם עסקה שנוצרת בשרת (`CreateTransaction`). היא מחוברת לספק תשלום של Medusa בשם `pp_nedarim_nedarim` ולמסד הנתונים של החנות. הסכום נלקח מסכום העגלה המחושב בשרת, כולל משלוח ומסים; סכומי Medusa v2 הם בשקלים/דולרים, ולא באגורות.

האתר החי מאוחסן ב־**Railway**, לפי אישור בעל האתר. כתובת ה־backend היא `https://admin.maasehrokeach.com`. קובצי Render הישנים במאגר אינם הגדרות הפריסה של האתר החי.

בבדיקת שירות `mechon-backend` ב־19 בנובמבר 2026 נמצא שורש `/book-store`, פקודת הבנייה `npm ci --include=dev --workspace=@dtc/backend --include-workspace-root=false && npm run build --workspace=@dtc/backend`, ופקודת ההפעלה `cd apps/backend/.medusa/server && npm run start`. לא הוגדרה פקודת Pre-Deploy. בהתאם לתוצר הבנייה, פקודת המיגרציות המיועדת לשדה זה היא `cd apps/backend/.medusa/server && npx medusa db:migrate --execute-safe-links`. שבעת משתני נדרים הוכנו כשינויים ממתינים; `NEDARIM_ENABLED` ו־`NEDARIM_ACCEPT_NEW_PAYMENTS` נשארו `false` עד למעבר מתואם. דומיין החנות שנצפה הוא `https://www.maasehrokeach.com`.

## הזרימה

1. בחירת הספק יוצרת ניסיון תשלום עם מזהה אקראי, סכום באגורות, מטבע ומזהה session שמגיע מההקשר המאומת של Medusa. נתוני אישור שהדפדפן שולח אינם משמשים לאימות.
2. אחרי אישור התקנון, `POST /store/carts/:id/nedarim` בודק את העגלה ואת אישור התקנון החתום, ומקים עסקה בשרת נדרים. הדפדפן מקבל רק `TransactionId` ו־`Key`. מסד הנתונים מונע הקמה מקבילה של אותה בקשה.
3. האייפרם בכתובת `https://www.matara.pro/nedarimplus/iframe/v3/` מקבל `StartPayment`. תגית `allow="payment"` מאפשרת ארנקים דיגיטליים. נתוני הכרטיס נשלחים ישירות לנדרים; הם אינם עוברים דרך השרת של החנות ואינם נשמרים בה.
4. נדרים שולחת `POST application/json` לכתובת `https://admin.maasehrokeach.com/hooks/nedarim/ATTEMPT/[ID]`. `[ID]` מוחלף במזהה ההכנה. זהו **Callback ברמת העסקה**, שהוא Webhook משרת לשרת; אין צורך להחליף Webhook קיים ברמת המוסד.
5. השרת מאמת HMAC-SHA256 על הבייטים המקוריים, חלון זמן של 5 דקות, מספר מוסד, `Param2`, סכום, מטבע ומזהה הכנה אם מופיע בגוף. בכרטיס/ארנק נדרש גם מספר אישור. עדכון שגיאה או הקמת הוראת קבע אינם מאשרים הזמנה.
6. אישור נשמר במסד לפני תשובת 200. אילוץ ייחודיות גלובלי על מזהה החיוב ופעולת compare-and-set מונעים שימוש באותו חיוב לשתי הזמנות. עדכון כפול מתקבל ללא חיוב או הזמנה נוספים.
7. הדפדפן דוגם רק את שרת החנות. הודעת `TransactionResponse` מבקשת בדיקת סטטוס; היא אינה אישור תשלום. גם פנייה ישירה ל־cart completion חייבת לעבור את בדיקת התשלום בשרת, ביחד עם בדיקת התקנון הקיימת.
8. משימה בכל דקה משלימה הזמנות ששולמו גם אם הדפדפן נסגר. כשל בהשלמה נשאר לעיבוד חוזר ומופיע ביומן. סכום שהשתנה או תשלום שהגיע לניסיון שהוחלף מחייבים בירור ואינם משחררים הזמנה אוטומטית.

## משתני סביבה והפעלה

בשרת ה־backend:

| משתנה | שימוש |
| --- | --- |
| `NEDARIM_ENABLED` | `false` בזמן ההכנה; `true` להפעלה אחרי הגדרת החתימה |
| `NEDARIM_ACCEPT_NEW_PAYMENTS` | `false` משהה פתיחת עסקאות חדשות בלי להסתיר את ספק התשלום. ברירת המחדל מאפשרת פתיחה |
| `NEDARIM_MOSAD` | מספר המוסד |
| `NEDARIM_API_VALID` | טקסט האימות שמופיע במסך מפתחות API |
| `NEDARIM_WEBHOOK_SECRET` או `STAMP_HMAC` | מפתח חתימת HMAC פעיל בנדרים פלוס, לפחות 32 תווים. כששניהם מוגדרים, `NEDARIM_WEBHOOK_SECRET` קובע |
| `NEDARIM_CALLBACK_BASE_URL` | `https://admin.maasehrokeach.com` — כתובת שרת ה־backend שאושרה על ידי בעל האתר |
| `NEDARIM_WEBHOOK_PREVIOUS_SECRET` | אופציונלי: המפתח הקודם בזמן סבב החלפה |
| `NEDARIM_API_PASSWORD` | מומלץ: מפתח `npk_` עם הרשאת `Manage3|GetHistoryJson` בלבד, להשלמת עדכונים חסרים |

אין להוסיף `NEXT_PUBLIC_` לשום סוד. `STAMP_HMAC` נתמך כשם חלופי למפתח חתימת ה־Webhook, לפי אישור בעל האתר. אפשר להשאיר את המפתח בשם הקיים בלי לשכפל אותו למשתנה נוסף.

אם מיזוג ל־`main` מפעיל פריסה אוטומטית, יש להכין מראש את משתני Railway, פקודת המיגרציות והפעלת ספק התשלום באזורים. בקוד זה תשלום ידני חסום ב־production גם כאשר `NEDARIM_ENABLED=false`: פריסה ראשונית כבויה אינה משמרת קופה המבוססת רק על `pp_system_default`. המעבר דורש פריסה מתואמת והפעלת הספק לפני פתיחת הקופה ללקוחות. כתובות מנהרה והגדרות מסד מקומיות אינן הגדרות ייצור.

1. בנדרים: הגדרות > API > Webhook > חתימת HMAC. העתיקו את המפתח לשרת, ואז הפעילו את החתימה. הפעלת HMAC משפיעה גם על עדכונים אחרים של אותו מוסד, ולכן יש לעדכן מראש כל מקבל Webhook קיים שמסתמך על אותה הגדרה. הקוד אינו משנה את הגדרות המוסד דרך API.
2. הגדירו את המשתנים בלשונית **Variables של שירות ה־backend ב־Railway**, בסביבה המיועדת לפריסה. `STAMP_HMAC` יכול לשמש כמפתח הקיים; אין צורך לשכפל אותו ל־`NEDARIM_WEBHOOK_SECRET`. הגדירו `NEDARIM_CALLBACK_BASE_URL=https://admin.maasehrokeach.com` ו־`NEDARIM_ENABLED=false` לפריסה הראשונית. משתני `.env` מקומיים אינם הגדרה של השירות בענן. מקור: https://docs.railway.com/variables
3. פרסו את הקוד המעודכן של ה־backend ושל ה־storefront. לפני הפעלת תשלומים הריצו את `npx medusa db:migrate --execute-safe-links` עבור מסד הנתונים של שירות ה־backend. ב־Railway אפשר להגדיר **Pre-Deploy Command** למיגרציות; יש להתאים את נתיב העבודה לשירות הקיים: הפקודה לעיל מתוך `book-store/apps/backend`, או `cd apps/backend && npx medusa db:migrate --execute-safe-links` אם שורש השירות הוא `book-store`. אין להניח שהמיגרציות רצות אוטומטית: צריך לבדוק את ההגדרה ואת יומן הפריסה של שירות Railway בפועל. מקור: https://docs.railway.com/deployments/pre-deploy-command
4. הפעילו את הספק באזורי ILS/USD דרך Medusa Admin > Settings > Regions, או הריצו מתוך `apps/backend`:

   ```sh
   npx medusa exec ./src/scripts/enable-nedarim.ts
   ```

   בסביבת הפריסה, מתוך `apps/backend/.medusa/server`, הקובץ המקביל הוא `./src/scripts/enable-nedarim.js`. לפני הפעלת הספק יש להגדיר `NEDARIM_ENABLED=true` בשירות ה־backend ולפרוס אותו מחדש, כדי שספק התשלום ייטען. הסקריפט מחליף את רשימת ספקי התשלום באזורי ILS/USD בנדרים פלוס. הוא אינו משנה אזורים במטבע אחר. יש לרענן את קאש צד הלקוח/ה־storefront אחרי שינוי ספקי האזור.
5. בדקו עסקה במוסד SANDBOX נפרד עם מפתח HMAC משלו ובכתובת HTTPS אמיתית. לפי מסמך נדרים, localhost אינו מתאים לבדיקה מלאה. מוסד 0 הציבורי אינו מאפשר מפתח HMAC או גישה להיסטוריה, ולכן אינו מספיק לבדיקת הזרימה המאובטחת הזו.

בתצורה הפעילה, בחירה בספק אחר חסומה ב־Store API וגם בהשלמת ההזמנה. ספק `pp_system_default`, שמאשר תשלום ללא סליקה, חסום בסביבת production גם כשנדרים כבויה. הספק הידני נשאר זמין לפיתוח מקומי בלבד.

## Google Pay, Apple Pay ו־bit

האייפרם מציג כרטיס, Google Pay, Apple Pay, bit והעברה בקליק רק כשהם זמינים במוסד ומתאימים למכשיר ולעסקה. בחירת האמצעי, CAPTCHA, סירובים, SMS/QR, והמתנה לאישור bit מטופלים בתוך האייפרם. המארח בודק `event.origin` וגם `event.source`, שולח ל־origin קבוע, מתאים גובה דינמית ומסיר את המאזין בפירוק הקומפוננטה.

העסקה היא חיוב רגיל בשקל או בדולר, בתשלום אחד. כך bit נשאר זמין בשקלים עד תקרת 3,600 ₪, כאשר המוסד מחובר. משתמשים ב־`Param2` בלבד, משום ש־`Param1` מסתיר bit והעברה בקליק. הדומיין כולל `www`, כפי שדורש Google Pay.

**Apple Pay דורש אישור דומיין חיצוני שאי אפשר להשלים בלי קובץ המוסד:**

1. בנדרים: שירותים מחוברים > Apple Pay > אישור דומיין. הזינו את דומיין ה־storefront והורידו את קובץ האימות.
2. הגדירו בשרת ה־storefront את `NEDARIM_APPLE_PAY_DOMAIN_ASSOCIATION` כתוכן המדויק של הקובץ הציבורי. לחלופין, אפשר להוסיף את הקובץ המדויק בנתיב public המתאים ולהסיר את route המקביל.
3. לאחר הפריסה בדקו שהכתובת `https://STOREFRONT/.well-known/apple-developer-merchantid-domain-association` מחזירה 200, ללא התחברות וללא redirect. נתיב ייעודי בקוד מוחרג מהפניית המדינה.
4. לחצו ״לבדיקה״ בממשק נדרים. כל דומיין, כולל www וכתובת ללא www, מאושר בנפרד. יש לשמור את הקובץ נגיש אחרי האישור.

## שחזור וניטור

לפי התיעוד, נדרים שולחת את ה־Callback **פעם אחת בלבד**. לפני ACK האישור נשמר במסד, ואחריו השלמת ההזמנה ניתנת לניסיון חוזר. עדיין ייתכן שהעדכון כלל לא הגיע לשרת החנות.

כאשר `NEDARIM_API_PASSWORD` מוגדר, משימה כל עשר דקות קוראת היסטוריה מאומתת באמצעות API. היא מצליבה הערה מדויקת `Mechon ATTEMPT`, סכום, מטבע, מספר אישור ומזהה חיוב ייחודי. `Param2` עצמו אינו נשמר בהיסטוריה. הסמן והזמן המוקדם לקריאה הבאה נשמרים במסד: לכל היותר 6 קריאות בשעה בין כל מופעי האתר, מתחת למגבלת 20 הקריאות של המוסד+IP. אם עוד יישומים משתמשים באותו מוסד/IP, יש לתאם את התקציב המשותף.

רישומי `[nedarim]` כוללים דחיית חתימות, נתונים לא תואמים, עדכון לניסיון שהוחלף וכשלי השלמת הזמנה. יש לנטר אותם בפלטפורמת האירוח. כתובות מקור מתועדות הן `18.196.146.117` ו־`18.194.219.73`; המקור העדכני הוא `https://www.matara.pro/nedarimplus/webhook-ips.txt`. HMAC הוא אימות המקור המחייב בקוד. IP לא מוכר נרשם כאזהרה, משום שמאחורי proxy אסור לסמוך על X-Forwarded-For שמגיע מהמבקש. אפשר להוסיף allowlist ב־proxy/חומת האש אחרי הגדרת שרשרת proxy אמינה.

אין חיוב נוסף בשלב capture. זיכוי וביטול כספי דרך Medusa חסומים עם הודעה מפורשת, עד להוספת תהליך נפרד שמבצע ומאמת אותם אצל הסולק; המערכת אינה מדווחת על החזר שלא בוצע. קבלות נדרים נשארות לפי הגדרות המוסד, משום שלא נשלח `ThirdPartyReceipt`.

## מקור וגבולות הבדיקה

### הצגת נדרים באתר המקומי בלי לשנות את האתר החי

בעל האתר אישר שה־backend הרגיל המקומי מחובר לאותו מסד נתונים של האתר החי. לכן הופעלה סביבת פיתוח נפרדת: PostgreSQL מקומי ב־`127.0.0.1:15433`, מסד `mechon_nedarim_dev`, ושרת Medusa ב־`127.0.0.1:9001`. לקובץ `.env.nedarim-local` יש קדימות בפרופיל זה והוא מוחרג מ־Git. `.env` המקורי לא הוחלף.

לסביבה המקומית הועתקו הקטלוג והגדרות האתר והקופה בלבד (71 טבלאות, 1,048 רשומות), ללא לקוחות, חשבונות והזמנות. ההעתקה מהמסד החי נעשתה בתוך טרנזקציית PostgreSQL עם `READ ONLY`. העתקת הקטלוג מסרבת לאפס מסד מקומי שכבר מכיל עגלות או הזמנות. ספק נדרים שויך לאזור המקומי בלבד; בבדיקה חוזרת האתר החי המשיך להחזיר `pp_system_default`.

הקמה ראשונית בלבד, מתוך `apps/backend`:

```sh
node scripts/nedarim-local.cjs init
node scripts/nedarim-local.cjs migrate
node scripts/nedarim-local.cjs copy-catalog
node scripts/nedarim-local.cjs enable
```

מסד PostgreSQL זה רץ במכולה `mechon-nedarim-dev`, עם volume מקומי בשם `mechon-nedarim-dev-data`. להפעלה חוזרת של ה־backend, מתוך `book-store`:

```sh
npm run dev:nedarim --workspace=@dtc/backend
```

לאחר שהשרת מוכן, הסקריפט מחבר את `storefront/.env.local` ל־`http://127.0.0.1:9001`. הוא שומר גיבוי מקומי של ההגדרות הקודמות בקובץ `.env.local.before-nedarim-local`, שגם הוא מוחרג מ־Git. ניתן לפתוח `http://127.0.0.1:8000/il`, להוסיף ספר לעגלה חדשה ולהמשיך לשלב אמצעי התשלום.

המשתנה `MEDUSA_BACKEND_URL` ב־storefront מגדיר את כתובת ה־backend לבקשות שיוצאות משרת Next בלבד. בפרופיל המקומי הסקריפט מגדיר אותו ל־`http://127.0.0.1:9001`, כדי שרינדור האתר ופעולות השרת לא יהיו תלויים בזמינות המנהרה הציבורית. בקשות מהדפדפן ממשיכות להשתמש ב־`NEXT_PUBLIC_MEDUSA_BACKEND_URL`. אם המשתנה הפנימי ריק, נשמרת ההתנהגות הרגילה לפי הכתובת הציבורית. כתובת ה־Callback לנדרים עדיין חייבת להיות כתובת HTTPS ציבורית פעילה.

לבדיקה דרך מנהרות HTTPS, אפשר להוסיף ב־`.env.nedarim-local` את `NEXT_PUBLIC_MEDUSA_BACKEND_URL` עם כתובת מנהרת השרת ואת `NEXT_PUBLIC_BASE_URL` עם כתובת מנהרת החנות. הסקריפט מסנכרן אותן ל־storefront בזמן ההפעלה. יש להגדיר גם `NEDARIM_CALLBACK_BASE_URL` לכתובת מנהרת השרת, להוסיף את מקור החנות ל־`STORE_CORS` ול־`AUTH_CORS`, ולהפעיל מחדש את סקריפט הפיתוח אחרי שינוי ההגדרות. כתובות מנהרה זמניות משתנות כשהמנהרה מופעלת מחדש; אין להעתיק אותן להגדרות האתר החי. לאחר בדיקת הנגישות אפשר להגדיר `NEDARIM_ACCEPT_NEW_PAYMENTS=true`; במוסד אמיתי השלמת התשלום תחייב באמת. Apple Pay דורש בנוסף אישור דומיין החנות וקובץ אימות מנדרים.

נדרים גלוי לבחירה, אך בפרופיל המקומי מוגדר `NEDARIM_ACCEPT_NEW_PAYMENTS=false`. השרת חוסם פתיחת עסקאות חדשות ב־503, ובממשק מוצגת סיבת ההשהיה לפי `NEXT_PUBLIC_NEDARIM_CHECKOUT_PAUSED`. הסקריפט מסנכרן את דגל התצוגה עם הגדרת השרת בזמן ההפעלה. אין להשתמש בכתובת ה־Callback של האתר החי עבור עסקאות של מסד פיתוח נפרד: לפני פתיחת תשלום אמיתי יש להגדיר כתובת HTTPS שמגיעה ל־backend המקומי הזה.

אומתו דרך HTTP: רשימת הספקים המקומית מחזירה `pp_nedarim_nedarim`, יצירת session מקומי עם הספק מחזירה 200, שני דפי checkout (payment ו־review) מחזירים 200 וכוללים את נדרים, ודף review מציג שהפתיחה מושהית. בקשת פתיחת תשלום חדש מוחזרת עם `nedarim_payments_paused`. כלי בדיקת הדפדפן לא היה זמין, ולכן האימות נעשה בתגובות השרת וב־HTML של הדפים.

### פענוח Callback ושחזור אישור חסר

ב־Callback אמיתי של כרטיס אשראי התקבלו שני שדות `TransactionId` באותו JSON: מזהה ההכנה ומזהה החיוב בהיסטוריה. הפענוח שומר את שני הערכים ומקבל את הכפילות רק אם הם תואמים למזהה ההכנה השמור בשרת ול־`ID` של החיוב. כפילויות אחרות נדחות. חתימת HMAC נבדקת על הבייטים המקוריים לפני הפענוח, ולאחריו עדיין נבדקים המוסד, הסכום, המטבע, `Param2` ואישור חברת האשראי.

`NEDARIM_API_PASSWORD` עם הרשאת `Manage3|GetHistoryJson` מאפשר קריאת היסטוריה מהשרת לצורך שחזור אישור שלא נקלט. הוא אינו מחליף את חתימת ה־Callback. לשחזור תשלום קיים בסביבת הפיתוח המבודדת, מתוך תיקיית ה־backend:

```sh
node scripts/nedarim-local.cjs recover ATTEMPT_ID HISTORY_PAYMENT_ID
```

הסקריפט קורא עסקה אחת בלבד מנדרים, דורש התאמה למזהה ההיסטוריה, להערה שהשרת יצר, לסכום, למטבע ולאישור, ושומר את האישור לפני השלמת ההזמנה. הפעלה חוזרת אינה יוצרת חיוב או הזמנה נוספים. עסקה שבוטלה (סכום אפס), זיכוי, הו״ק או עסקה שאינה תואמת נדחים. אין לסמן תשלום כשולם על סמך הודעה בדפדפן או העתק מייל.

### הרצת בדיקות האינטגרציה

הבדיקה מפעילה שרת Medusa אמיתי על פורט `19001` ומסד PostgreSQL נפרד על `15432`. היא מריצה את המיגרציות ואת חיבור ספק התשלום בפועל, ודוגמת את מסלולי ה־HTTP של החנות וה־Callback. רק שירות נדרים החיצוני מדומה: אין קריאת סליקה, אין חיוב ואין משלוח דואר. הסקריפט מחליף במפורש את כתובת מסד הנתונים ואת מפתחות הבדיקה ואינו משתמש במסד או במפתחות מתוך `.env`.

הקימו PostgreSQL זמני לבדיקות בלבד:

```sh
docker run --detach --name mechon-nedarim-local-test \
  -e POSTGRES_USER=nedarim_test -e POSTGRES_PASSWORD=local-test-only \
  -e POSTGRES_DB=postgres -p 127.0.0.1:15432:5432 postgres:16-alpine
```

מתוך `book-store` הריצו:

```sh
npm run test:nedarim:local --workspace=@dtc/backend
```

הבדיקות כוללות נעילת הסכום המחושב בשרת כולל משלוח, שימוש חוזר באותה עסקת הכנה, דחיית Callback ללא חתימה או בסכום שגוי, חסימת הזמנה ללא אישור, השלמת הזמנה אחת אחרי עדכון חתום עבור ארבעת אמצעי התשלום, קריאות מקבילות וייחודיות מזהה חיוב במסד. נבדקים גם השלמת הזמנה באמצעות משימת הרקע אחרי סגירת דפדפן, שחזור Callback חסר מהיסטוריה מאומתת, ואכיפת מגבלת הקריאות בין קריאות מקבילות. הן אינן בדיקת סליקה חיה של Google Pay / Apple Pay / bit אצל הספק. בדיקה מלאה מול נדרים דורשת מוסד SANDBOX וכתובת HTTPS ציבורית שמגיעה לשרת הבדיקות; ניתן להשתמש במנהרה לשרת המקומי בלי לפרוס את האתר החי.

כל עשרת התרחישים עברו מקומית מול PostgreSQL ושרת HTTP אמיתיים: שמונת תרחישי התשלום והנעילות עברו בהרצה מלאה, ושני תרחישי ההתאוששות שנוספו עברו בהרצה ממוקדת. הבדיקה מצאה ותיקנה פגם בטעינת הסכום: בחירת `shipping_methods.id` בלבד השמיטה את עלות המשלוח מחישוב Medusa; כעת נטענים גם נתוני המשלוח, המסים וההתאמות, ונבדקת התאמה של 123.45 ₪ במוצרים ועוד 10 ₪ משלוח לסכום חיוב נעול של 133.45 ₪.

ההטמעה מבוססת על `NedarimPlus-API-2.md`: שיטה 3 והזרקת עסקה מהשרת, CreateTransaction, אימות תשלום, חתימת HMAC והיסטוריית עסקאות. נדרשת בדיקת SANDBOX מלאה מול מוסד מוגדר כדי לאשר את מבנה ה־Callback בפועל לכל אמצעי. נתון חסר או שגוי יידחה; אין מסלול fallback שמאשר תשלום לפי הדפדפן.

בבדיקה המקומית: בניית קוד ה־backend הצליחה עם בניית Admin כבויה; בדיקת TypeScript של ה־storefront עברה; לאחר הוספת בדיקות ההשהיה עברו 85 בדיקות יחידה ב־backend ו־14 בדיקות תשלום/הסכמה ב־storefront. בבדיקת כלל בדיקות ה־storefront שנערכה קודם עברו 58 מתוך 66; שמונה הכשלים הם במבחני Google Login קיימים, שה־mock שלהם אינו מספק את התלות `@lib/util/google-avatar`. קבצי ההתחברות האלה לא שונו במשימה.

בדיקת חיבור אמיתית עם `Amount=0` אישרה שמספר המוסד ו־ApiValid תקינים, ללא יצירת עסקה או חיוב. נתיב אימות Apple Pay נבדק ב־HTTP מקומי והגיע ל־route ללא redirect; ללא קובץ מוגדר הוא מחזיר 404 במכוון. כלי בדיקת הדפדפן לא היה זמין, וסליקה מלאה בארנקים/bit ובדיקת Callback אמיתי טרם בוצעו. הסליקה הושארה כבויה ב־`.env` המקומי. מצב משתני הסביבה והפריסה ב־Railway טרם נבדק באמצעות גישה לחשבון. בדיקת ה־backend הציבורי אישרה ש־`/health` מחזיר 200, בעוד בקשת POST ללא חתימה לנתיב ה־Callback החדש החזירה 404; לכן לא אומתה זמינות ההטמעה בשרת החי.
